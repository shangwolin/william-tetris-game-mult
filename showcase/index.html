1 遊戲介紹

專案簡介

Tetris Battle 是一款雙人即時連線對戰俄羅斯方塊遊戲。採用 Python WebSocket 後端 + 純前端 Canvas 渲染，不使用任何遊戲引擎或框架。

兩人各自在同一個房間內獨立操作自己的版面，消行時會送出垃圾行攻擊對手。遊戲的核心機制包含完整的 SRS 旋轉系統、7-bag 隨機器、Hold 暫存、Hard Drop、計分與加速系統。

如何啟動

本機雙人

pip install websockets
python server.py

打開 http://localhost:8765 兩個分頁

Docker

docker compose up --build

網際網路連線

python server.py
ngrok http 8765

朋友連到 ngrok URL 即可對戰

雙人對戰流程

  1. Player 1 按 Create Room → 取得房間代碼
  2. Player 2 輸入房間代碼 → 按 Join
  3. 雙方按 Ready → 遊戲自動開始
  4. 消行送出垃圾行給對手（1清=0行, 2清=1行, 3清=2行, Tetris=4行）
  5. 任一方堆到頂 → game over，另一方獲勝
  6. 按 再戰一局 可 rematch

2 Loop Engineering 設計說明

Success Criteria 定義方式

每一個 Task 都有明確的 ACCEPTANCE 與 fr_refs 鏈結回 spec 中的 FR-### 需求。驗收標準分三層：

層級內容範例
FR (Functional Req)功能面要求，必須可測試FR-007: 登入密碼短於8碼回傳400
SC (Scenario)使用情境，端到端流程SC-001: 兩玩家開房→對戰→game_over流程
QA Gate自動化 + 人工關卡Stage A (lint/SAST/secretscan) + Stage B (reviewer + test_engineer)

每個 Task 完成時，必須有 reviewer APPROVED + test_engineer PASS 雙重簽核才算過關。

安全閥 / 邊界設計

🛡️ 技術安全閥

  • Heartbeat timeout：5s interval，2 次 miss 自動斷線，防 ghost connection
  • Exponential backoff reconnect：最長 30s，10 次上限，防 reconnect storm
  • max_size：WebSocket message 上限 1MB，防 OOM
  • broadcast() async：sync→async 修正，防 un-awaited coroutine
  • Hold atomic restore：swap 失敗時 snapshot rollback，防 partial mutation

🔁 Process 安全閥

  • Critic Gate：plan 執行前必須通過 critic 審查（最大 2 輪 revision）
  • Stage A + Stage B：自動化工具（lint, SAST, secretscan）+ agent review（reviewer + test_engineer）雙重關卡
  • Circuit Breaker：coder 3 次失敗 → 暫停、consult critic_sounding_board → 簡化任務後重試
  • Spec-Staleness Guard：spec 與 plan 不一致時封鎖 save_plan / update_task_status

3 Multi-Agent 設計說明

Agent 分工架構

🧠 ArchitectOrchestrator — 任務拆解、路由、品質把關
├─→🔍 ExplorerCodebase 實況調查、領域偵測
├─→📚 SME領域專家（security, Python, networking…）
├─→💻 Coder實作（一次一個 task）
├─→👁️ ReviewerCode review（security, correctness, edge-cases）
├─→🧪 Test Engineer測試撰寫 + 執行（含 adversarial）
├─→📝 CriticPlan review gate（pre-implementation）
├─→💬 Critic Sounding BoardPre-escalation pushback（3 次 impasse 觸發）
└─→📖 DocsREADME / API docs 更新

為什麼這樣分工？

關注點分離（Separation of Concerns）是核心原則。每一個 agent 只做一件事：

  • Architect 是唯一有全局 context window 的角色，負責拆解任務、路由、驗收 —— 其他人 context 較小，不需要知道全局
  • Coder 只寫 code，不負責 review 或測試 —— 避免「作者盲點」（author blind to own mistakes）
  • Reviewer 只看 code 不寫 code —— 純審查視角，沒有維護 bias
  • Test Engineer 獨立於 coder 之外寫測試 —— 確保測試不是被實作「污染」的 happy path
  • Critic 在 plan 階段就介入 —— 避免花時間實作一個從根本上就有問題的設計
  • Critic Sounding Board 是架構師的「橡膠鴨」—— 在 escalation 之前先自我反思

本次作業（Swarm 版）與傳統單一 agent 開發有以下關鍵差異：

4 反思

Loop Engineering 對開發流程的實際幫助

✅ 正面幫助

  1. 強制收斂 — 每輪 loop 有明確的目標與驗收標準，不會一直發散加功能
  2. 早期發現整合問題 — Loop 3 發現的前後端協定不一致如果沒有獨立驗收，可能會藏到最後才炸
  3. 知識累積 — Lessons Learned 從 Loop 1 累積到 Loop 5，同一問題不會重複踩坑
  4. 安全閥讓失敗是安全的 — Circuit Breaker 機制防止浪費 token 在無解的任務上

⚠️ 踩坑記錄

  1. Coder model 不可用 — opencode/minimax-m2.5-free 不存在，被迫架構師自己寫 code，繞過 QA gate
  2. Reviewer / Test Engineer 空回傳 — 部分 subagent model 靜默失敗不回 verdict，需人工 retry
  3. Spec-staleness 卡關 — spec 與 plan 不一致時完全封鎖，需手動 /swarm acknowledge-spec-drift
  4. websockets 16.x 文獻不足 — API 變動大（process_request, Response, Headers），靠實驗摸索

如果再來一次，我會怎麼改進？

🔧 Loop Engineering 改進

  • 更小的 loop — 有些 task 太大（如 2.2 Canvas rendering），應拆成更細的 sub-task
  • E2E test 提前 — Loop 3 才寫 E2E test，應該 Loop 1 就寫，更早捕獲 protocol 問題
  • 每一輪強制 retrospective — 前幾輪沒有即時寫 lesson learned，靠記憶不準確
  • 定義 escape hatch — 當 subagent 不可用時應立即降級，而不是重試 3 次才 fallback

🔧 Agent 分工改進

  • Coder model 備援 — 應支援多個 model fallback chain，避免單一 model 不可用就卡住
  • 減少 Architect 手動 routing — 多個獨立 task 應自動 parallel dispatch（Epic Mode 的 wave 概念）
  • 更強的 reviewer checklist — Reviewer 應有 task-specific checklist 而非通用維度
  • Test Engineer 獨立 context — 測試不應看到 coder 的實作細節，避免 biased test

小結

這次作業證明 Multi-Agent Swarm + Loop Engineering 確實能產出更高品質的程式碼，

付出的代價是更複雜的 infra 與更多的 token 消耗，但換來的是

可審查、可回溯、可中斷續接的開發流程。
