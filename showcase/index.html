1 遊戲介紹

專案簡介

Tetris Battle 是一款雙人即時連線對戰俄羅斯方塊遊戲。採用 Python WebSocket 後端 + 純前端 Canvas 渲染，不使用任何遊戲引擎或框架。兩人各自在同一個房間內獨立操作版面，消行送出垃圾行攻擊對手。

核心機制：SRS 旋轉系統 + wall kick、7-bag 隨機器、Hold 暫存、Hard Drop、計分（100/300/500/800 × level）、垃圾行攻擊（0/1/2/4 行）、遊戲加速系統。

開發方式：透過 Agent Swarm（多代理人並行協作）與 Loop Engineering（自我迴圈驗收），在 3 個 sessions 內完成 5 個 Loops、15 個 Tasks。

雙人對戰流程

兩台電腦連線步驟

  1. Host 啟動伺服器：python server.py
  2. Host 打開 http://localhost:8765 → Create Room
  3. 區網連線：Client 連 http://<Host-IP>:8765（Windows 關閉防火牆或開 8765 port）
  4. 網際網路連線：Host 執行 ngrok http 8765，Client 連 ngrok URL
  5. Client 輸入房間代碼 → Join → 雙方 Ready → 開戰！

2 Loop Engineering 設計說明

2.1 Success Criteria — 怎麼定義驗收標準

在每一輪 loop 啟動前，該輪的 success criteria 已經透過 spec.md 與 plan.json 明確定義。採用三層架構：

層級對應 HW2 四階段定義方式範例
FR (Functional Requirement)Planning Agent可測試的功能規格，每條有唯一 FR-### 編號FR-005: 消行時應對對手送出對應 garbage lines
SC (Scenario)Planning Agent端到端使用情境，驗證跨功能流程SC-001: 兩玩家開房→ready→對戰→game_over 流程正確
QA GateValidator / Governance AgentStage A（lint, SAST, secretscan）+ Stage B（reviewer + test_engineer）lint PASS + reviewer APPROVED + test PASS

每一輪的通過條件 = 該輪所有 Task 的 FR 實作完成 + Stage A/B 全數綠燈，不得以「看起來差不多」作為驗收標準。

2.2 Loop 跑了幾輪？每一輪發生了什麼？

5 輪，對應計畫中的 5 個 Phases：

Loop 1 — 後端核心

3 tasks | ✅ Stage A+B 通過
server.py（RoomManager, heartbeat, game loop）+ game.py（Board, SRS, 7-bag, scoring, garbage）
整合測試 28/28 → reviewer APPROVED → drift verifier APPROVED

Loop 2 — 前端 UI

4 tasks | ✅ Stage A+B 通過
index.html 大廳 + Canvas 渲染 + DAS/ARR 鍵盤控制 + 觸控按鈕 + WebSocket 客戶端（exponential backoff reconnect）

Loop 3 — 前後端整合

3 tasks | ✅ Stage A+B 通過
lobby 配對流程、game flow（state→render→game_over→rematch）、斷線處理
關鍵發現：前後端協定名稱不一致（type:state vs state_update, action:drop vs hard_drop）— E2E test 捕獲

Loop 4 — Docker + 修復

3 tasks | ✅ Stage A+B 通過
Dockerfile multi-stage、README、修復 websockets 16.x API 變更（process_request, Response, Headers）

Loop 5 — PWA + 迴圈記錄

2 tasks | ✅ 完成
docker-compose.yml、manifest.json、progress.md 完整 loop log、本成果發表頁面

2.3 安全閥與邊界

🛡️ 技術安全閥

  • Loop Boundary：最多 5 輪，超過即停止回報
  • Heartbeat timeout：5s interval，2 次 miss 自動斷線
  • Exponential backoff reconnect：最長 30s，10 次上限
  • max_size：WebSocket message 上限 1MB
  • broadcast() async：修正 sync→async
  • Hold atomic restore：snapshot rollback

🔁 流程安全閥

  • Critic Gate：plan 執行前須通過 critic 審查（max 2 輪 revision）
  • Stage A + Stage B 雙重關卡
  • Circuit Breaker：coder 3 次失敗 → 暫停 → 諮詢 → 簡化或上報
  • Spec-Staleness Guard：spec 與 plan 不一致時封鎖寫入
  • Token 成本：無硬性限制，但 circuit breaker 防止無限浪費

完整記錄：progress.md

3 Multi-Agent 設計說明

3.1 Agent 分工架構

對應 HW2 的四代理人概念，本次作業將其擴展為可並行的 Agent Swarm 架構：

HW2 Agent 1 Planning → 🧠 Architect + 🔍 Explorer + 📚 SME 任務拆解、領域調查、專家諮詢
HW2 Agent 2 Governance → 📝 Critic + 💬 Critic Sounding Board plan 審查、pre-escalation 反思
HW2 Agent 3 Coding → 💻 Coder 實作（一次一個 task）
HW2 Agent 4 Validator → 👁️ Reviewer + 🧪 Test Engineer code review + 測試 + adversarial
→ 📖 Docs 文件更新（新增角色）

完整 Swarm 架構圖

🧠 Architect ← Orchestrator（最大 context window）
  ├─→ 🔍 Explorer — codebase 實況調查、領域偵測
  ├─→ 📚 SME — 領域專家（security, Python, networking）
  ├─→ 💻 Coder — 實作（一次一個 task）
  ├─→ 👁️ Reviewer — code review（security, correctness, edge-cases）
  ├─→ 🧪 Test Engineer — 測試撰寫 + 執行 + adversarial
  ├─→ 📝 Critic — plan review gate（pre-implementation）
  ├─→ 💬 Critic Sounding Board — pre-escalation pushback
  └─→ 📖 Docs — README / API docs 更新

4 反思

Loop Engineering 對開發流程的實際幫助

✅ 正面幫助

  1. 強制收斂 — 每輪 loop 有明確的目標與驗收標準，不會一直發散加功能
  2. 早期發現整合問題 — Loop 3 發現的前後端協定不一致，如果沒有獨立驗收，可能會藏到最後才炸
  3. 知識累積 — Lessons Learned 從 Loop 1 累積到 Loop 5，同一問題不會重複踩坑
  4. 安全閥讓失敗是安全的 — Circuit Breaker 機制防止浪費 token 在無解的任務上
  5. 可中斷續接 — progress.md 記錄最後完成的 loop 狀態，關掉 session 後下次回來知道從哪裡繼續

⚠️ 踩坑記錄

  1. Coder model 不可用 — opencode/minimax-m2.5-free 不存在，架構師被迫自己寫 code，繞過 QA gate
  2. Reviewer / Test Engineer 空回傳 — 部分 subagent model 靜默失敗不回 verdict，需人工 retry
  3. Spec-staleness 卡關 — spec 與 plan 不一致時完全封鎖，需手動 acknowledge
  4. websockets 16.x 文獻不足 — API 變動大（process_request, Response, Headers），靠實驗摸索
  5. Loop Governance 太晚定義 — Success Criteria 和 Loop Boundary 是在全部開發完後才補文件的，應在 Loop 1 開始前就定義

如果再來一次，我會怎麼改進？

🔧 Loop Engineering 改進

  • 更小的 loop — 有些 task 太大（如 Canvas rendering），應拆成更細的 sub-task
  • E2E test 提前到 Loop 1 — 更早捕獲 protocol 問題
  • 每一輪強制 retrospective — 前幾輪沒有即時寫 lesson learned，靠記憶不準確
  • 定義 escape hatch — 當 subagent 不可用時應立即降級，而不是重試 3 次才 fallback
  • Loop Governance 事前定義 — Boundary / Criteria / Guardrail 應在開發前就寫明

🔧 Agent 分工改進

  • Coder model 備援 — 應支援多個 model fallback chain
  • 減少 Architect 手動 routing — 獨立 task 應自動 parallel dispatch（Epic Mode wave 概念）
  • 更強的 reviewer checklist — Reviewer 應有 task-specific checklist 而非通用維度
  • Test Engineer 獨立 context — 測試不應看到 coder 的實作細節，避免 biased test
  • 分散式 agent 監控 — 每個 subagent 應有獨立的 timeout 與 retry 策略，而非全靠 architect 輪詢

小結

本次作業證明 Multi-Agent Swarm + Loop Engineering 確實能產出更高品質的程式碼——

代價是更複雜的 infra 與更多的 token 消耗，但換來的是

可審查、可回溯、可中斷續接的開發流程。

Loop 不是魔法——它只是把「驗收」從人腦移到系統裡，讓它不會被跳過。
